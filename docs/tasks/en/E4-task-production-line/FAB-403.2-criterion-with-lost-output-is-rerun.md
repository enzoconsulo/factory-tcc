# FAB-403.2 · A criterion that fails with no output is rerun

> ✅ Done · Subtask of FAB-403 · Stage **E4 — Task production line**

## The idea

Do not fail a delivery when what failed was the transport of the command's output, not the command.

## What was done

`Factory.Criteria` gained a second retry policy: when a criterion fails with a non-zero exit code and the output comes back empty, the command is rerun up to 2 times and stops at the first run that brings output. The single retry for environment failures (timeout, broken tool) stays the same.

## Why it came up

On Windows, with many processes started at the same time, the Erlang port driver loses the short output of a fast process: the exit code arrives right and the output arrives empty. Measured: 0% loss up to 4 concurrent processes, about 4% with 24 and about 10% with 48. Without the output, `FailureClass` misses the broken-tool signal (for example, "unrecognized argument") and classifies the failure as a delivery error. With the rerun, the loss drops to about 0.3%.

## How it was built

- `single_run/4` returns the result together with the exit code
- Only fires on a non-zero code: a timeout (no code) keeps the single retry, and a failed spawn always carries an output
- If no rerun brings output, the last one stays, marked as rerun

## Acceptance criteria

- [x] A 1st run with no output followed by a 2nd with output keeps the 2nd output
- [x] A failure that already carries output on the 1st run is not rerun
